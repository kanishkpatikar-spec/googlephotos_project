# GOOGLE PHOTOS CORE EXPERIENCE — AI-NATIVE PRODUCT PROJECT

## SOURCE OF TRUTH

The following project has been assigned by reviewers.

Treat the reviewer-provided problem statement as the absolute source of truth.

Do NOT reinterpret the problem into a generic photo-search project.

Do NOT change the business goal.

Do NOT narrow or expand the assignment without evidence.

Do NOT fabricate research, interviews, user quotes, survey responses, usability-test results, metrics, or conclusions.

The final project must directly address every requirement in the reviewer brief:

1. Build an AI-powered discovery engine
2. Break down the business metric
3. Validate the opportunity through 5–6 user interviews
4. Define the problem
5. Build a functional AI-native MVP
6. Test the MVP with at least 3 users
7. Define success metrics
8. Identify risks and mitigation steps

The product context is Google Photos Core Experience.

The strategic business goal is:

**Increase the percentage of users who successfully retrieve a photo they remember but cannot precisely describe when they start searching.**

This project is specifically about retrieval when memory is incomplete.

It is NOT about improving Google Photos search in general.

---

# 1. PROJECT OBJECTIVE

Build a complete end-to-end product case study and functional prototype that investigates:

**Why do users fail to retrieve a photo that they know exists when they remember something about it but cannot precisely describe it?**

The project must discover the answer through research rather than assuming it.

The project should investigate situations such as:

“That small café we went to during our Goa trip.”

“The picture of the medicine I took when I was sick last year.”

A user may remember that the photo exists but may not remember:

* exact date
* exact location
* exact name
* album
* filename
* exact searchable text
* exact event
* exact visual details

The system should investigate what users actually remember instead.

Possible remembered information might include:

* rough time
* people involved
* trip or event
* visual appearance
* reason the photo was taken
* something that happened around the photo
* approximate place
* object category
* text fragment
* emotion
* purpose
* sequence relative to another event
* whether it was a screenshot/photo/document

These are examples only.

The research must determine the real patterns.

The research system should help answer questions such as:

### Memory

Do users remember:

* who

* why

* visual appearance
* event context

### Search Behavior

What does the user type when they cannot remember the correct search term?

Do they start broad?

Do they change dates?

Do they use people?

Do they try multiple synonyms?

Do they give up?

### Failure

Where does retrieval actually fail?

Possibilities include:

* user cannot express the memory
* system misunderstands their clues
* relevant photo never appears
* relevant photo appears but is buried
* user cannot recognize the correct result
* user cannot refine the query
* system treats uncertain information too literally
* system cannot use contextual/relational clues

Do not assume which one is dominant.

### Workarounds

What do users do when search fails?

Examples may include:

* manually scrolling timeline
* browsing albums
* searching locations
* searching people
* checking WhatsApp
* asking another person
* searching Google Maps
* checking calendar
* searching screenshots
* trying multiple keywords
* abandoning the task

Again, discover rather than assume.

# 9. PART 2 — BUSINESS METRIC DECOMPOSITION

**Successful retrieval of vaguely remembered photos**

Do not assume retrieval success depends only on search relevance.

```text
Successful Vague Retrieval

├── Relevant candidates are retrieved
```

# 10. DEFINE RETRIEVAL SESSION

For this project, create an operational definition.

A **vague-memory retrieval session** occurs when:

1. The user believes a specific visual asset exists.
2. The user wants to retrieve it.
3. At the beginning of the task, the user lacks enough precise information to identify it directly.

A successful retrieval occurs when the intended target asset is found.

For controlled testing, each task should have a known target image where possible.

# 33. PART 8 — RISKS AND MITIGATION

Create a risk register specific to the final solution.

Consider at minimum:

## Privacy

Photo libraries are deeply personal.

Mitigation could include:

* local processing where practical
* explicit consent
* deletion controls
* minimal retention
* no training usage
* clear data policy in prototype

## Incorrect AI Interpretation

The system might misunderstand partial memory.

Mitigation:

* editable assumptions
* confidence representation
* refinement
* fallback retrieval

## Hallucination

LLMs may invent information that does not exist in the library.

Mitigation:

* ground generated responses in indexed assets
* provenance
* avoid unsupported claims

## Retrieval Quality

Relevant assets may never enter candidate pool.

Mitigation:

* hybrid retrieval
* multiple retrieval signals
* larger candidate generation before reranking

## Latency

Multimodal AI can be slow.

Mitigation:

* preprocess library
* cache embeddings
* asynchronous indexing
* lightweight reranking where appropriate

## Cost

Multimodal models can be expensive.

Mitigation:

* preprocessing
* embedding reuse
* selective LLM calls
* smaller models for classification

## User Trust

Users may not understand why photos are surfaced.

Mitigation:

* transparent reasoning where useful
* clear controls
* user correction

## Research Bias

Public complaints may over-represent unhappy users.

Mitigation:

* use multiple sources
* validate with interviews
* distinguish prevalence from severity

## Interview Bias

Users may poorly recall past retrieval behavior.

Mitigation:

* use real retrieval tasks
* screen sharing / think-aloud where possible
* Critical Incident Technique

Add risks specific to the final MVP.

# 50. IMPORTANT DEVELOPMENT RULE

Before implementing a feature, ask:

**Which requirement from the reviewer brief does this support?**

If no clear answer exists, do not prioritize it.

Before showing a research conclusion, ask:

**What evidence supports this?**

If none exists, label it a hypothesis.

Before building an AI capability, ask:

**Why is intelligence required here?**

If deterministic software can solve it equally well, use deterministic software.

Before reporting success, ask:

**Did the user actually retrieve the intended target?**

Do not use engagement as a substitute for retrieval success.
